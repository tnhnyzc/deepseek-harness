# Agent Note: desktop stage 5 — native desktop capability providers

Status: implemented

English | [中文](2026-08-25-desktop-native-capabilities.zh.md)

## Problem

Stage 5 (SPEC stage 5) must give the desktop its native capability boundary: DSH-owned operations that touch the OS — choosing a directory, opening a path with the default application — must flow `DSH client UI → DSH API → DSH runtime capability/provider → native.request → Electron main → Electron/OS API → native.response → DSH runtime → DSH result`, with the renderer never calling Electron for a DSH-owned operation. Stage 2's temporary arrangement — the desktop runtime child spawning osascript/Zenity/KDialog/COM choosers of its own through the pinned `dsh-host-directory-picker-native` provider — is unsuitable: a forked child should not be the process that owns OS dialogs, and the host's default-application openers were running as subprocesses out of the child instead of through Electron. The pinned source has exactly two consumers (the directory-picker seat and the `ApiProxyDefaults` openers) and no others (no file picker, no OS notifications), so the method set is closed to them.

## Decision

**The channel.** A private runtime↔main channel rides the supervisor's fork IPC — never the renderer, never the stage 3 transport port, never localhost. The supervisor demuxes `native.request` and `native.abort` off the child channel ahead of the transport relay (`apps/desktop/src/main/runtime.ts`, a `RuntimeNative` surface beside `RuntimeTransport`), and the runtime child's bridge demuxes the reverse direction the same way (the transport process adapter ignores it by the transport discriminant). The closed wire contract lives in `apps/desktop-runtime/src/native.ts`, shipped as the new `@deepseek-ai/dsh-desktop-runtime/native` subpath (exports + tsdown entry + tsconfig `paths` facade): `native.request` (`directory.pick` / `path.open` with a non-empty, NUL-free, ≤32768-char path), `native.response` (success, or the closed failure codes `unknown-method`, `malformed-request`, `dialog-failed`, `open-failed`, `cancelled`), `native.cancel` (main→child on generation teardown), and `native.abort` (child→main once, when the caller's abort terminates an in-flight request that was already dispatched). Every free-text field (`message`, both `reason`s) is bounded to `NATIVE_MAX_DIAGNOSTIC_CHARS` (512) and enforced by the parsers at the wire boundary — a producer truncating its own outbound value is not the contract. No `native.call(method, payload)`; no DSH business vocabulary anywhere in the messages; the method, code, and bound vocabularies are constants the parsers enforce.

**Runtime side.** `createNativeBridge` (`apps/desktop-runtime/src/native-bridge.ts`) is the child's request/response client: unique request ids, the caller's `AbortSignal` held for the operation's whole lifetime (abort settles with the `AbortError` terminal, the operation becomes terminal, and every late response or cancel is ignored), stale and duplicate id refusal, and every pending operation settled with `channel-closed` on dispose or supervisor disconnect — no operation survives the channel. A mid-flight abort also crosses the abandonment to main as exactly one `native.abort` (bounded string signal reason, or a fixed fallback) — but only if the request was already dispatched; a never-dispatched request fabricates no remote cancel, and a response that wins the race produces no abort. The DSH seats consume it: `DesktopDirectoryPicker` (`apps/desktop-runtime/src/directory-picker.ts`) is the new `ctx.directoryPicker` provider — the same native seat, one stable `{ kind: 'native', pick }` capability object, `pick` delegated to the bridge — and the runtime entry provides it plus the `nativeOpeners` service, disposing the bridge before the fiber on teardown.

**The provider swap.** The desktop composition (`apps/desktop-runtime/src/composition.ts`) keeps the stage 2 overlay shape — disable the web `auto` `directory-picker` row, insert a provider — but the insert is now the desktop provider module, built to `dist/directory-picker.js` beside the runtime entry and loaded by file URL (a `pathToFileURL` of the sibling path, platform-correct on POSIX and Windows). The Loader imports module specifiers, which is why the file path crosses as a URL rather than a bare path.

**Main side.** `createNativeCapabilities` (`apps/desktop/src/main/native-capabilities.ts`) is the closed OS registry — `dialog.showOpenDialog({ properties: ['openDirectory'] })` and `shell.openPath(path)` — over an injectable port so the behavior is testable without an Electron runtime; it maps failures onto the closed codes and bounds every diagnostic by the protocol's own `NATIVE_MAX_DIAGNOSTIC_CHARS`. `createNativeChannel` (`apps/desktop/src/main/native-channel.ts`) validates each request through the shared parser (a malformed request is a refusal, never an OS call; a readable id gets `unknown-method` or `malformed-request`, an unreadable one is dropped as uncorrelatable), dispatches, and settles each request with exactly one terminal: a success, a closed-code failure, or — on `teardown(reason)` — a `native.cancel` for every still-pending request, after which late results and new requests are dropped. A `native.abort` marks its request logically terminal immediately: the id leaves the pending set, nothing is sent back, a malformed abort is dropped fail-closed, and the OS operation's late completion — a visible dialog cannot be portably dismissed — is dropped in `finish` instead of emitted as a stale response. The channel is per-generation: `index.ts` recreates it on every supervisor close (teardown the old one, create and re-arm a fresh one; the supervisor clears the message handler before the close handler runs, so the re-registration survives) and tears the final one down on `before-quit` — a single long-lived channel would die on the first generation end and leave every later generation's requests without an answerer.

**Upstream extension (one, guarded): M4.** `ApiProxyService` (`packages/host/apiproxy/src/index.ts`) reads an optional provided service `nativeOpeners` (`{ openPath?, openTextFile? }`, typed in `src/api/native-openers.ts` with its `Context` merge) and forwards the present members as its `ApiProxyDefaults` openers. By absence the package's own native openers and `canOpenNativePath()` detection stand, so the web app is unchanged. The desktop provides `openPath` (bridged to `shell.openPath`); `canOpenPaths()` then reports the desktop as able to open. `openTextFile` is deliberately not bridged: the pinned Electron `shell.openPath` takes no options and has no text-editor intent, so `settings.openDocument` keeps the DSH native text opener (macOS `open -t`), where a text editor is actually requested.

**Cancellation semantics.** The DSH contract is unchanged and is where the business codes live: `host.pickDirectory` maps a caller abort to `cancelled` and any other failure to `internal` (`api-proxy.ts:2842-2869`); `openTarget` does the same for opens. Cancellation crosses both directions as separate concepts: a caller abort settles the DSH call as `cancelled` in the child and crosses one `native.abort` to main, which marks the request logically terminal and drops the late OS completion; a main-issued `native.cancel` (generation teardown) is a channel failure, not an operator cancel — it settles the DSH call as `internal` carrying the reason. The distinction is logical versus physical: Electron offers no API to close an already-visible dialog, so in the abort case the dialog may stay on screen and finish in the background; its result is dropped at main, and the dialog's own cancel is the operator's only close.

**Architecture pins.** The boundary spec (`apps/desktop/tests/boundary.spec.ts`) gains: main may import only the two closed protocol subpaths (transport + native); the four native-capability source files are scanned for DSH business RPC literals like the transport files; the renderer and preload may contain none of the native protocol tags (`native.request`, `native.response`, `native.cancel`, `native.abort`, `directory.pick`, `path.open`); and the composition no longer mounts the temporary `-native` provider while keeping the single-provider overlay. Real acceptance is `apps/desktop-runtime/tests/native-boot.spec.ts`: it forks the built runtime, plays the main side over the child IPC, and pins `host.describe.canOpenPath`, pick success/cancel, open success/failure, the cancel mapping, client-abort termination of an in-flight pick and of an in-flight open (each crossing a real `native.abort` whose late result is dropped), healthy channel reuse after the abort, and the shutdown exit. `apps/desktop/tests/native-integration.spec.ts` answers the same forked runtime with the REAL main-side channel over a controllable OS port, pinning the abort end-to-end at the main edge: the pending set empties immediately, the late dialog completion emits nothing, and the next request settles normally.

## Consequences

- The stage 2 host-native chooser is no longer mounted by the desktop; the pinned `-native` package remains for browser/host surfaces. One `ctx.directoryPicker` provider per composition, as always.
- The desktop runtime's build gains two entries (`native.js`, `directory-picker.js`) and the app's build order is unchanged (runtime first).
- The pinned source diverges in exactly one place (the M4 seam in `dsh-host-apiproxy`), guarded by service absence; the web app's behavior is bit-for-bit the prior behavior.
- The fork IPC now carries a second message family; the stage 3 transport protocol is untouched, and the stage 4 stream-cancellation correction is preserved (the real-boot suite re-runs it green).
- Deferred with pinned-source reasons: file picker, OS notifications, external-URL opening — all absent in the pinned source (§6.3), and the closed method set stays exactly the two existing consumers.

## Alternatives considered

- Keep the stage 2 subprocess choosers in the child — rejected: a forked child owning OS dialogs and default-app spawns is exactly the boundary the stage exists to remove, and the dialog's parent window would be absent from the process that shows it.
- A renderer-side native bridge (`window.desktop.pickDirectory`) — rejected: it would make the renderer the origin of DSH-owned operations and bypass the DSH service seat, inverting the ownership the pinned source establishes.
- Extend the stage 3 transport protocol with native frames — rejected: the transport is the renderer's generic carrier with its own framing, credits, and per-generation channel; the capability channel is main↔child only and rides the fork IPC with the supervisor's generation identity.
- Inject the openers through `ApiProxyDefaults` from a desktop fork of the gateway — rejected: it would duplicate the gateway; the one-line guarded `nativeOpeners` service keeps the DSH API and the error/cancel mapping in the package that owns them.
- Bridge `openTextFile` through `shell.openPath` anyway — rejected: the pinned API has no text-editor intent, so it would open documents in the default (often non-editor) application and change `settings.openDocument` behavior for no capability gain.
