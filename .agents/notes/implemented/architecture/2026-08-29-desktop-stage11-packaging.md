# Agent Note: desktop stage 11 — reproducible self-contained packaging and process containment

Status: implemented

English | [中文](2026-08-29-desktop-stage11-packaging.zh.md)

## Problem

Stages 1–10 produced a working, hardened Electron app that runs from the repository: `pnpm --filter @deepseek-ai/dsh-desktop start` boots the app against the workspace's `node_modules` and the DSH pinned in `packages/`. That is a development surface, not a product. A distributed build must boot on a machine with no repository, no `pnpm`, no global `node`, and no network at first launch, and it must do so reproducibly: the same locked inputs must yield the same release unit. It must also survive the two platform-specific hazards the development surface hides — the native modules that must match the *runtime* ABI rather than Electron's, and the Windows process-tree lifetime that a spawned DSH command tree would otherwise outlive the app. Stage 11 (SPEC §25–28) is the packaging pass: a reproducible, self-contained, per-platform release unit plus the Windows containment guarantee.

## Decision

**The release unit is atomic and identity-bearing.** Desktop shell, Electron, the bundled Node, the pinned DSH, the client assets, and the native prebuilds ship as one unit. `apps/desktop/scripts/packaging/build-manifest.ts` writes `build-manifest.json` (schema v2, eleven fields) into the artifact: the desktop version, the DSH commit and version, the bundled Node version and its SHA-256, the Electron version, the desktop runtime protocol version, the platform/arch, and a `closureFingerprint` — a stable hash over the staged closure's sorted `consumer@version -> dep@version` resolution *edges*, not merely the name/version set, so two closures that differ only in which version a consumer resolves are different fingerprints. The reader (`readBuildManifest`) re-checks the schema version and every field on load, so a manifest that drifts from the code that wrote it fails at the boundary, not at runtime. The fingerprint is the reproducibility handle: identical locked inputs produce an identical closure graph and thus an identical fingerprint.

**DSH runs under the bundled standalone Node, never under Electron.** This is the load-bearing ABI rule. The runtime child is forked with the artifact's own `resources/node/<target>/node` as `execPath` (`apps/desktop/src/main/runtime.ts`, `runtime-paths.ts`), so every native module the runtime loads — `koffi`, `sharp`, and their prebuilds — must match the *standalone Node* ABI for the host target, not Electron's. `electron-rebuild` is deliberately not run against standalone-runtime modules; running it would retarget them to the Electron ABI and break the very isolation the two-ABI split exists to provide. The bundled Node is the pinned `node-versions.json` entry for the host target, downloaded and SHA-256-verified by `apps/desktop/scripts/bundle-node.ts` (`installNodeTarget`), so the Node binary in the artifact is the same bytes on every build.

**The dependency closure is audited, then staged as a flat root with per-consumer collision shadows.** `apps/desktop/scripts/packaging/closure-audit.ts` walks the runtime entry's *production* import graph and records every consumer→dependency resolution edge, every same-name/different-version collision, and the graph fingerprint. The real graph contains dependency cycles (`@deepseek-ai/cordis` ↔ `cordis-plugin-include`, and longer cycles through the plugin loader and the API proxy chain), so any staging plan that nests *every* dependency under *every* consumer location never terminates on cycles and explodes on diamond-heavy subgraphs; a plan computed per consumer location did loop forever and die at 4 GB. The adopted layout (`apps/desktop/scripts/packaging/closure.ts`): a non-colliding package instance is copied **once** to `<root>/node_modules/<name>` — Node's upward walk reaches it from any consumer location, and cycles among root packages are ordinary `require` cycles — while a colliding instance is copied under each colliding consumer's staged location, fixed-point over collision edges only. On the real graph this is 496 copies (436 root + 60 shadows) for 452 instances and 1968 edges, staged in ~15 s. The staged audit is written into the artifact's extraResources and the layout verifier re-checks the graph against the manifest fingerprint. The asar entry check normalizes each `listFiles` entry to forward slashes before comparison: `@electron/asar` joins header paths with `path.join`, so on Windows the entries arrive backslash-separated and a literal POSIX `includes` check fails on a correct artifact.

**The artifact layout is ASAR-plus-unpacked-resources, verified by scan.** `@electron/packager` packs the Electron app into `app.asar` with asar integrity enabled; the large, path-sensitive, or native resources are staged outside it under `Resources/` (the renderer bundle, the bundled `node/`, the `runtime/` tree, `build-manifest.json`, and `licenses/`). The asar mirrors the development checkout layout — `dist/main/index.js`, `src/preload/index.cjs`, and a manifest that keeps `type: module` — because the shell resolves the checked-in preload through `app.getAppPath() + '/src/preload/index.cjs'` and the same expression must hold in both worlds; a flattened asar broke the packaged preload with a silent ENOENT (no bridge, renderer crash on first IPC). `apps/desktop/scripts/packaging/verify-layout.ts` runs 33 checks against the built artifact: the manifest is present and well-formed, the bundled Node is present and matches the manifest's SHA-256, every closure anchor (`koffi-<target>`, `sharp-<target>`, `dsh-base`, and `sharp-libvips-<target>` on the targets whose sharp graph takes libvips as a separate package — darwin, linux, musl; the win32 wrapper bundles its libvips DLLs internally, so the check skips that anchor there) is staged once and resolvable from its consumer, the asar contains the expected entries and no stray `node_modules`, and the nine fuses read back to their release values. A check failure fails the pipeline; it is not a warning.

**All nine Electron fuses are set explicitly, before any signature.** `apps/desktop/scripts/packaging/fuses.ts` pins the complete fuse set for Electron 43 with `strictlyRequireAllFuses: true` — no fuse is left to an Electron default. `RunAsNode` and the file-privilege fuses are disabled; `EnableEmbeddedAsarIntegrityValidation` and `OnlyLoadAppFromAsar` are enabled. `EnableNodeCliInspectArguments` is deliberately fused **off**: the release binary exposes no Node-level inspector, so no live-code path into the main process (this is what forces the packaged-app smoke to drive the app through the browser DevTools endpoint instead — see below). The flip happens before signing because a fuse flip rewrites the binary and invalidates any existing signature; on Apple Silicon an ad-hoc re-sign is mandatory afterward. Two mechanical traps are pinned by construction: `@electron/fuses`' `FuseV1Options` is a *numeric* enum, so `Object.values` yields both directions and the code iterates the explicit `DESKTOP_FUSE_INDICES` (numeric keys `0..8`) instead; and `flipFuses` returns the count of binary *slices* it rewrote (the sentinel), not the number of fuses changed, so the report says "set 9 fuses across 1 binary slice(s)".

**Signing is credential-gated and reported as configured-versus-executed.** There is no single signing mode. On macOS, `apps/desktop/scripts/packaging/package.ts` signs with the `CSC_NAME` keychain identity via `@electron/osx-sign` when one is present (hardened runtime, the built-in entitlement set that already grants `com.apple.security.cs.allow-jit`), and notarizes via `@electron/notarize` when `APPLE_ID`/`APPLE_APP_SPECIFIC_PASSWORD`/`APPLE_TEAM_ID` are set; with no credentials it falls back to an ad-hoc `codesign --force --deep --sign -`, which is launchable on the build host after the fuse flip but is not a distributable signature. On Windows it signs with `@electron/windows-sign` when `CSC_CERTIFICATE_FILE`/`CSC_KEY_PASSWORD` are set, else ships unsigned. On Linux there is no signing. The `package-report.json` records, per step, whether signing and notarization were *configured* (credentials present) and *executed*, so a build that could not notarize is never misreported as one that did.

**D4 is a real Windows process-tree guarantee, pinned to the SDK ABI and executed only where it can be proven.** When the runtime root dies, every process in the DSH tree — including DSH's own detached command trees — must die with it. On Windows this is implemented in the runtime child (`apps/desktop-runtime/src/windows-job.ts`) with a Win32 Job Object created with `KILL_ON_JOB_CLOSE` and the process assigned to it via `AssignProcessToJobObject`, using `koffi` against kernel32 with struct layouts mirrored exactly from the Windows SDK headers (`JOBOBJECT_BASIC_LIMIT_INFORMATION` 64 bytes with `LimitFlags` at offset 16, IO counters 48 bytes, extended limit information 144 bytes, information class 9, `PROCESS_SET_QUOTA` for the basic limit) and an install-time sizeof gate. Current SDKs declare a fourth `SetInformationJobObject` parameter — the buffer length, which current kernels verify (a three-argument FFI leaves the register undefined and the kernel answers `ERROR_MORE_DATA`, 24, regardless of layout); the four-argument form is the portable one, older kernels ignoring the extra register. `apps/desktop-runtime/scripts/check-windows-job-abi.ts` compiles a C probe with the toolchain's `cl.exe` against the machine's own SDK headers, compares the compiler's sizes, offsets, and constants against the koffi declarations and the pinned values, and executes one real `SetInformationJobObject` (four-argument form, memberless job), so a layout or signature the kernel no longer accepts fails the build on the shipping machine. The koffi declarations register the three structs before any function signature names them — koffi resolves the type name at the `func` call, and a signature declared before its struct is an unknown type. The acceptance script (`apps/desktop/scripts/d4-acceptance.ts`) runs in two modes — the dev runtime and `--packaged <artifact>` — and in each forks a child that spawns a grandchild, kills the child's root with `taskkill /F /PID` (deliberately not `/T`, so the Job Object — not the taskkill tree flag — is what kills the grandchild), and asserts the grandchild is gone within the deadline while the acceptance process itself survives. Both modes run **only** in the `desktop-windows` CI job, on a real Windows kernel; they are never claimed as locally exercised on macOS.

**Outer-job hosts boot in an explicit externally-contained fallback; D4 is validated only where the product job installs.** Hosted Windows runners and current Windows 11 builds place every service-hosted process tree inside an OS-owned Job Object (the runtime's pre-boot `IsProcessInJob` probe returns membership; the outer job's limit flags are not queryable from a user process). When the tree is already a member of an outer job, `windows-job.ts` does not install the product job: it reports `mode: 'externally-contained'` (best-effort outer limit flags via `QueryInformationJobObject(NULL)`), the runtime writes a loud `d4 fallback:` stderr warning naming that the product Job Object is NOT installed and D4 is NOT validated in this mode, and the tree's lifetime is the outer job's responsibility. Every other containment init error stays fail-closed. The containment mode rides the `d4.acceptance-report` message (`product-job` with the two descendant pids, or `externally-contained`), and the acceptance gate treats the two modes differently: a `product-job` report runs the full kill-the-root drill and fails the lane on any breach; an `externally-contained` report exits 0 with a loud `SKIP (externally contained)` marker so the CI lane can run, but the run is never counted as a D4 validation — a real validation requires an unjobbed launch context where the product job assignment succeeds. Unit tests pin all three behaviors (product path with the full koffi call sequence, fallback on probe hit and on error-5 assignment, fail-closed on unrelated errors and on a missing pre-1809 probe export).

**The execution smokes are the distribution proof — four of them, all under the artifact's own bytes.** (1) The clean-copy boot smoke (`scripts/packaging/smoke-runtime.ts`) forks the packaged `runtime/dist/index.js` with the *artifact's own* bundled Node, a fresh `DSH_HOME` in a temp dir, and a minimal `PATH` (`/usr/bin:/bin:/usr/sbin:/sbin`), and asserts the child reaches `runtime.ready` with a `dshVersion` equal to the manifest's DSH version. (2) The resolution smoke (`scripts/packaging/smoke-resolution.ts`) verifies the staged closure's resolution edges under the bundled Node with an explicit Node-style `node_modules` walk (nearest-wins, bounded at the runtime root) instead of `require.resolve` — `require.resolve` is too strict: types-only packages (`undici-types`, `csstype`), exports-only-without-`main` packages (`@img/sharp-*`, `dsh-web-frontend`), and binary-only packages fail it identically in the real workspace, so the layout contract is nearest-wins placement, checked against `package.json` name+version. (3) The native-module execution smoke (`scripts/packaging/smoke-native-modules.ts`) executes `sharp` (libvips) and `koffi` (FFI) under the bundled Node. (4) The packaged-app smoke (`scripts/smoke-packaged-app.ts`) launches the **actual packaged Electron executable** with a fresh temp user-data dir, a constrained `PATH`, and a seeded single-workspace registry, and proves the shipped artifact reaches the real DSH UI (client tree booted, composer editable), carries the security baseline (sandbox, contextIsolation, no nodeIntegration, webSecurity, no webview, DevTools denied, the default-deny permission policy with its single clipboard exception), runs the packaged runtime (ready under the bundled Node with the pinned DSH version), publishes a bounded real carrier round trip (a composer turn against a scripted 127.0.0.1 provider), proves the native capability channel twice — a structurally malformed `path.open` (a NUL byte) that the shell's strict parser must return as `malformed-request` over the channel, a full request→response cycle with no OS involvement and identical on every platform, and the product's own `openPath` on a path guaranteed not to exist, which must settle as `open-failed` where the OS settles at all and records a bounded abort on a headless host that cannot settle it (no session, no file handler) — keeps zero product TCP listeners (the runtime process; the shell's only listener is the smoke's own DevTools endpoint, which the Linux runtime child co-owns through inherited fds and the `ss`-based check filters out as shell-co-owned), and survives the Stage 9 crash/restart drill (abnormal root death, the window survives, the UI's Restart affordance brings a fresh generation to readiness with a new runtime pid). The shell is driven over the browser-level DevTools endpoint (`--remote-debugging-port=0`, a Chromium switch unaffected by the release fuses, read from the binary's own stderr) with a minimal CDP session, because Playwright's Electron support needs the Node inspector seam that `EnableNodeCliInspectArguments` being off removes — on the fused binary Playwright's launch hangs forever. UI input is synthetic DOM under CDP `Runtime.evaluate` (the React-controlled composer takes the native value setter + `input` event, Enter as a `keydown`). Every CDP round trip is bounded by a hard timer (an unresponsive renderer counts as "not yet", so the wall-clock deadlines always fire), and the composer gate's timeout dumps its own cause — the textarea's `readOnly`/`disabled`/placeholder/phase, the runtime child's diagnostic tail, and the hero text showing whether the seeded workspace is visible to the picker. The smoke self-skips without a built artifact or a GUI session; the CI lanes run it per platform (Linux under Xvfb; the packaged `chrome-sandbox` ships deliberately not setuid and the runner's AppArmor blocks unprivileged user namespaces, so the launch adds `--no-sandbox` — a harness flag; the app's own sandbox baseline is asserted from the page).

**Each CI runner packages its own platform, for all four targets.** Cross-host packaging is rejected by design: the closure's native prebuilds are host-specific, so a macOS runner cannot stage a correct Windows closure. `ci.yml` defines four required jobs — `desktop-macos` (macos-latest, darwin-arm64), `desktop-macos-x64` (macos-14, darwin-x64), `desktop-windows` (windows-latest, win32-x64 — which also runs the Win32 ABI probe and the D4 acceptance in dev and `--packaged` modes), and `desktop-linux` (ubuntu-latest, linux-x64 — with the Electron system dependencies and an Xvfb display so the packaged-app smoke actually runs) — each running `pnpm --filter @deepseek-ai/dsh-desktop run package` and uploading its distributable archive plus `package-report.json` as the run evidence. Each lane is a clean-tree build: the desktop build is self-contained (the workspace `build:lib` first — the renderer resolves `@deepseek-ai/dsh-client-web`'s built `lib/` — then the desktop runtime, whose build is `tsc -b && tsdown` because its tsdown entries are tsc outputs, then main and renderer), and the desktop host tsconfig deliberately omits the `packages/client/web` reference — that edge pulls the client face into the host program, and the client face imports typert-generated `*/remote` modules that exist only after the host tsdown, so a clean-tree host build fails with TS2307 (`client/modules` stays referenced; the renderer remains covered by the client aggregate). They are in `all-checks-passed.needs`, so a broken package on any platform, or a D4 regression, blocks the merge. The pipeline itself snapshots the repository root `package.json` and `pnpm-lock.yaml` at the start and verifies them before writing the report, so packaging can never silently rewrite repository files.

## Facts the stage settled

- The packager's `filenamify` does **not** replace spaces (they are not reserved characters), so the output directory, the `.app`, and the executables keep the product name's spaces verbatim on every platform — `DeepSeek Harness Desktop-<platform>-<arch>` and `DeepSeek Harness Desktop.app`. The artifact-path helpers preserve the spaces; they do not hyphenate.
- A scoped store package's real path is `.pnpm/<id>/node_modules/@scope/<name>`; the container is the three path segments after the `.pnpm` segment, found with `lastIndexOf`. A store package's own `.bin`-only `node_modules` masks the container and must be checked before it.
- The production closure contains dependency cycles, and a staging plan that nests every dependency under every consumer location does not terminate on cycles (observed: infinite loop, 4 GB OOM). Flat root + per-consumer collision shadows terminates: root packages resolve for every consumer through Node's upward walk, and only the 8 colliding instances (16 instances, 43 edges) need per-consumer shadows.
- `require.resolve` on a bare specifier is the wrong probe for a staged layout: types-only, exports-only-without-`main`, and binary-only packages fail it in the real workspace too. The layout contract is nearest-wins `node_modules` placement, verified by an explicit bounded walk comparing `package.json` name+version.
- The fused release binary has no Node inspector (`EnableNodeCliInspectArguments` off) but does honor `--remote-debugging-port=0`; the browser DevTools endpoint is the seam an external observer has, and it drives the entire packaged-app smoke. Playwright `_electron.launch` on the fused binary hangs at the inspector handshake.
- The asar must mirror the development checkout layout (`dist/main` + `src/preload`, `type: module` in the manifest): the shell resolves the preload through `getAppPath() + '/src/preload/index.cjs'` in both worlds. A flattened asar surfaces as a silent preload ENOENT and a renderer crash on the first IPC.
- The packaged runtime executable lives at `resources/node/<target>/node` — the shell's path expression and the staging layout must agree, or the first boot fails with a spawn ENOENT.
- Session workspace attach validates the session cwd against the stored workspace path one-sidedly: it canonicalizes the cwd through the product's `realpathNormalize` (`fs.realpath` from `node:fs/promises`) and compares it string-equal to the stored path as-is, so the stored path must already be a fixed point of that exact canon. `registry.create()` canonicalizes before storing; a seed that bypasses it must seed through the same `realpathNormalize`, not the sync `realpathSync` — the GitHub windows runner's `%TEMP%` is an 8.3 short name (`C:\Users\RUNNER~1\...`) where the sync and promise forms disagree, and on macOS and many Linux hosts the temp root is a symlink (`/var` → `/private/var`).
- The runtime child receives a curated environment, not the shell's: the test-only `DSH_DESKTOP_SMOKE=1` gate must be forwarded through the supervisor's `extraEnv` for the runtime to publish smoke facts and the bridge to expose the smoke method.
- The distributable archive is `DeepSeek Harness Desktop-<version>-<platform>-<arch>.zip` (macOS via `ditto`, Windows via PowerShell `Compress-Archive`) or `.tar.gz` (Linux via `tar`), each with a `.sha256` sidecar — created after fuses and signing, so the archive carries the finalized bytes.
- `@electron/fuses`' `FuseV1Options` is a numeric enum: `Object.values` returns both name and value directions, so fuse iteration must use the explicit numeric index list.
- `@electron/osx-sign` 2.x `sign({app, identity})` defaults `hardenedRuntime` on and uses the built-in entitlements (which include `allow-jit`); there is no top-level `hardenedRuntime`/`entitlements` option in 2.7.0. `notarize` takes `appPath`, not `app`. `@electron/windows-sign` `hashes` is a cross-package `const enum` a string literal cannot satisfy and must be cast.
- The standalone-Node ABI rule means the runtime's native modules are retargeted to the bundled Node, and `electron-rebuild` must never touch them; the two ABI worlds (Electron for the shell, standalone Node for the runtime) are the whole point of the split.
- `SetInformationJobObject` in current SDKs takes a fourth argument — the information buffer length, which current kernels verify. A three-argument FFI declaration leaves the argument register undefined and the kernel answers `ERROR_MORE_DATA` (24), not a layout error, so the failure masquerades as a data problem; the four-argument form is portable because older kernels ignore the extra register.
- koffi resolves type names in a `func` signature at the `func` call: a struct must be registered (`koffi.struct` with a name) before any signature references it by name, and a pointer argument to a kernel struct is declared as `'<Struct> *'` — declaring the struct itself passes it by value.
- The D4 gate scripts are typechecked under the desktop host tsconfig like every other host script: the source-mode child imports the runtime's `./windows-job` subpath (the runtime's fifth tsdown entry, mirroring the `./transport` and `./native` subpaths) instead of a cross-project relative import, which a project-references build rejects (TS2878).
- A forked child inherits the parent's fds: on Linux `ss -tlnp` attributes a co-owned listener (the shell's DevTools endpoint, held by the runtime through inheritance with the same fd number) to the runtime pid, so a per-pid listener assertion must filter sockets the shell co-owns; macOS `lsof -a -p` scoping never surfaced it.
- A headless Linux host cannot settle Electron `shell.openPath` (no session bus, no file handler): the native channel is proven instead by a parse-rejected round trip (a NUL-byte path returns `malformed-request` over the channel, no OS involved), and the OS probe records a bounded abort instead of an OS verdict.
- On Windows `pnpm` is a `.cmd` shim that `CreateProcess` cannot exec without a shell: the pipeline spawns it with `shell: true` on `win32` only, and checks `result.error` so a failed spawn names itself instead of dying as `exit null`.
- sharp 0.35.x on win32: the `@img/sharp-win32-x64` wrapper declares no dependencies and bundles its libvips inside the tarball (`lib/libvips-42.dll`, `lib/libvips-cpp-8.18.3.dll`); `sharp`'s optionalDependencies include the win32 wrapper but no win32 libvips package (darwin/linux/musl do). A pnpm lockfile with no `@img/sharp-libvips-win32-x64` edge is therefore correct, and pnpm 11 silently drops any manually-added win32 libvips edge on a non-frozen install — do not chase it as a missing dependency. (`supportedArchitectures` read from `.npmrc` is ignored by pnpm; pnpm 11 takes workspace config from top-level `pnpm-workspace.yaml` keys.)
- GitHub-hosted `windows-latest` is job-contained: a self-assignment via `AssignProcessToJobObject` fails there with win32 error 5 because the runner's own orphan-cleanup Job Object already owns the tree (membership is inherited and cannot be left). The externally-contained fallback is the designed operating mode for such hosts, not a workaround.
- A Windows 11 26200 build job-contains every automation-reachable process tree on the user's VM: both the sshd chain and the WinMgmt/CIM (`Win32_Process::Create`) chain report outer-job membership via `IsProcessInJob`, and the interactive-desktop double-click runs reached the VM through an sshd-parented tree as well. On such a build the product-job kill drill has no unjobbed launch context to run from; the fallback path is what executes there, end to end (healthy boot under the artifact's bundled Node plus the loud `SKIP (externally contained)` marker).
- A CDP `Runtime.evaluate` against a hung renderer never resolves, so a poll loop that only checks its wall-clock deadline *between* evaluates can hang forever (the deadline becomes unreachable). The packaged-app smoke bounds every evaluate with a hard timer and counts an unresponsive round trip as "not yet", which is what makes its deadlines real — an unbounded await was observed to hold a Windows pipeline with no verdict for 30+ minutes.
- Node re-quotes argument text when it builds a Windows CreateProcess command line (backslash-escaping inner quotes), so a `cmd /c` command containing quoted toolchain paths must go through a wrapper batch file, which cmd parses verbatim.
- A clean tree has no typert artifacts: the desktop host tsconfig must not reference `packages/client/web` (its client face imports generated `*/remote` modules → TS2307 in the host build); the desktop build runs the workspace `build:lib` before the renderer, and the desktop runtime builds `tsc -b && tsdown` (its tsdown entries are tsc outputs).
- GitHub's ubuntu-24.04 runners block unprivileged user namespaces under AppArmor and the packaged `chrome-sandbox` is deliberately not setuid, so the packaged-app smoke launches the real binary with `--no-sandbox` (a harness flag; the app's sandbox baseline is asserted separately from the page).

## Consequences

- Stage 11 exit criteria met with no pinned-source change and no new Electron surface: the release unit is reproducible (manifest + closure-graph fingerprint), self-contained (boot smoke under the artifact's own Node, minimal PATH), per-platform (four required CI lanes, one per target), execution-proven (four smokes under the artifact's own bytes, the last one on the real binary and real UI), and process-contained on Windows (D4: ABI-pinned to the shipping kernel, the externally-contained fallback proven end to end on job-contained hosts, the product-job kill drill pending a non-job-contained host).
- New scripts: `apps/desktop/scripts/packaging/{package,staging,closure-audit,closure,build-manifest,fuses,verify-layout,smoke-runtime,smoke-resolution,smoke-native-modules,release-format}.ts`, `apps/desktop/scripts/smoke-packaged-app.ts`, `apps/desktop-runtime/scripts/{check-windows-job-abi.ts,windows-job-abi-probe.c}`; new devDependencies `@electron/asar`, `@electron/osx-sign`, `@electron/windows-sign` (alongside the existing `@electron/packager`, `@electron/fuses`, `@electron/notarize`); `koffi ^3.1.0` in `apps/desktop-runtime`.
- New coverage: `apps/desktop/tests/packaging.spec.ts` (fuse pin, per-platform binary path, archive-format pin, manifest reader, and an opt-in full layout verify against a built artifact), `apps/desktop/tests/closure-audit.spec.ts` (a synthetic pnpm-shaped fixture — store containers, symlinked links, workspace packages, and a non-colliding cycle as a regression guard — plus read-only assertions on the real repository graph), `apps/desktop/tests/packaged-app.spec.ts` (self-skipping wrapper over the real-binary smoke), and the extended `ci-workflow.spec.ts` (the four required per-platform lanes, the Windows-only ABI probe + D4 dev/packaged acceptance, the Linux Xvfb display, and the per-lane archive uploads).
- D4's Windows execution and the Windows/Linux/darwin-x64 packaging are CI-proven; the Win32 ABI gate additionally ran on a local Windows 11 VM (which surfaced the four-argument `SetInformationJobObject` requirement — the ABI probe now executes the call against the shipping kernel). That VM's build job-contains every automation-reachable process tree (sshd, WinMgmt/CIM, and the runner agents alike), so the product-job kill drill has no unjobbed launch context on it: the externally-contained fallback executed there instead, end to end, in every context tried — which is the designed behavior for job-contained hosts. D4 product-job validation on a real kernel therefore stands on the ABI probe (the real four-argument call accepted on the shipping kernel) plus the unit-pinned koffi call sequence, with the end-to-end kill drill pending a non-job-contained Windows host; the fallback and the gate's loud `SKIP (externally contained)` marker are the standing evidence that job-contained hosts boot healthy and are never misreported as validated. The four CI lanes are the standing evidence for the full target matrix, and the Developer ID / notarization / Windows-certificate signing paths are configured-not-executed where credentials are absent.
- The four remaining CI jobs run on upstream self-hosted fleet labels (`dsh-ubuntu-24-04-16core`, `dsh-windows-2025-16core`) that a fork registers no runners for, so `all-checks-passed` cannot be fully green on the fork: the four desktop lanes and the public-runner jobs are the fork-satisfiable gate.
- The updater (SPEC §28) is recorded as the release boundary but not built; stage 11 produces the artifact the updater would later move.

## Alternatives considered

- Running DSH under Electron's Node instead of a bundled standalone Node — rejected: it would collapse the two-ABI split, force `electron-rebuild` over the runtime's native modules, and tie the DSH runtime to Electron's V8/ABI release cadence; the split is what lets the runtime track a pinned, checksummed Node.
- Copying `node_modules` wholesale instead of a store-derived closure — rejected: a `node_modules` snapshot carries the developer's full tree (devDependencies, hoisted duplicates, platform-foreign prebuilds) and is not a lockfile-pinned, reproducible unit; the closure is the minimal, hashable set.
- Nesting every dependency under every consumer location (per-consumer staging for all edges) — rejected after direct observation: the real graph's dependency cycles make the plan non-terminating (infinite loop) and its diamond-heavy subgraphs make it exponential (4 GB OOM); flat root + per-consumer collision shadows is the terminating layout that preserves exact per-consumer resolution.
- Driving the packaged-app smoke through Playwright's Electron support — rejected: it requires the Node inspector (`--inspect`), which the `EnableNodeCliInspectArguments` fuse deliberately removes from the release binary; the browser DevTools endpoint is the seam an external observer actually has, and flipping the fuse back would reopen a live-code path into the main process.
- Cross-host packaging (one runner builds all platforms) — rejected: native prebuilds are host-specific, so a single host cannot stage a correct closure for the other platforms; each runner packages its own platform.
- Leaving fuses to Electron defaults and flipping only the security-critical ones — rejected: a default is an implicit contract that changes with the Electron version; `strictlyRequireAllFuses` plus an explicit nine-fuse set makes the artifact's capability surface a reviewed, pinned fact.
- Making the packaging jobs non-blocking (observational) like `windows-native` — rejected for v1: a broken package or a D4 containment regression is a release defect, and the whole point of the stage is that the distributed unit actually boots; the four jobs are required.
- Signing ad-hoc on the CI lanes and calling it done — rejected: ad-hoc is a build-host launchable signature, not a distributable one; the pipeline instead distinguishes configured (credentials present) from executed and reports it, so a release can require the real credential path without the CI lanes needing secrets.
