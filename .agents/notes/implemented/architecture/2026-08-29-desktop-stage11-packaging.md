# Agent Note: desktop stage 11 — reproducible self-contained packaging and process containment

Status: implemented

English | [中文](2026-08-29-desktop-stage11-packaging.zh.md)

## Problem

Stages 1–10 produced a working, hardened Electron app that runs from the repository: `pnpm --filter @deepseek-ai/dsh-desktop start` boots the app against the workspace's `node_modules` and the DSH pinned in `packages/`. That is a development surface, not a product. A distributed build must boot on a machine with no repository, no `pnpm`, no global `node`, and no network at first launch, and it must do so reproducibly: the same locked inputs must yield the same release unit. It must also survive the two platform-specific hazards the development surface hides — the native modules that must match the *runtime* ABI rather than Electron's, and the Windows process-tree lifetime that a spawned DSH command tree would otherwise outlive the app. Stage 11 (SPEC §25–28) is the packaging pass: a reproducible, self-contained, per-platform release unit plus the Windows containment guarantee.

## Decision

**The release unit is atomic and identity-bearing.** Desktop shell, Electron, the bundled Node, the pinned DSH, the client assets, and the native prebuilds ship as one unit. `apps/desktop/scripts/packaging/build-manifest.ts` writes `build-manifest.json` (schema v1, nine fields) into the artifact: the desktop version, the DSH commit and version, the bundled Node version and its SHA-256, the Electron version, the desktop runtime protocol version, the platform/arch, and a `closureFingerprint` — a stable hash over the staged closure's `name@version` set. The reader (`readBuildManifest`) re-checks the schema version and every field on load, so a manifest that drifts from the code that wrote it fails at the boundary, not at runtime. The fingerprint is the reproducibility handle: identical locked inputs produce an identical closure set and thus an identical fingerprint.

**DSH runs under the bundled standalone Node, never under Electron.** This is the load-bearing ABI rule. The runtime child is forked with the artifact's own `resources/node/<target>/node` as `execPath` (`apps/desktop/src/main/runtime.ts`), so every native module the runtime loads — `koffi`, `sharp`, and their prebuilds — must match the *standalone Node* ABI for the host target, not Electron's. `electron-rebuild` is deliberately not run against standalone-runtime modules; running it would retarget them to the Electron ABI and break the very isolation the two-ABI split exists to provide. The bundled Node is the pinned `node-versions.json` entry for the host target, downloaded and SHA-256-verified by `apps/desktop/scripts/bundle-node.ts` (`installNodeTarget`), so the Node binary in the artifact is the same bytes on every build.

**The dependency closure is a lockfile-pinned copy from the pnpm store, not a `node_modules` snapshot.** `apps/desktop/scripts/packaging/closure.ts` walks the runtime entry's import graph and copies each resolved package verbatim from the pnpm store into a flat staging tree. The store path of a package is the fragile part: a package's real modules live at `.pnpm/<id>/node_modules/<name>`, but a scoped package lives at `.pnpm/<id>/node_modules/@scope/<name>`, and some store packages carry their own `.bin`-only `node_modules` that masks the container. `depContainer` locates the container by finding the `.pnpm` path segment (`lastIndexOf`) and taking the three segments after it, which is correct for both scoped and unscoped packages and for the masked cases. Getting this wrong does not fail the build; it silently stages an incomplete tree and the packaged runtime cannot resolve a module at boot — the closure went from 339 to 750 packages once scoped-store dependencies were found.

**The artifact layout is ASAR-plus-unpacked-resources, verified by scan.** `@electron/packager` packs the Electron app into `app.asar` with asar integrity enabled; the large, path-sensitive, or native resources are staged outside it under `Resources/` (the renderer bundle, the bundled `node/`, the `runtime/` tree, `build-manifest.json`, and `licenses/`). `apps/desktop/scripts/packaging/verify-layout.ts` runs 33 checks against the built artifact: the manifest is present and well-formed, the bundled Node is present and matches the manifest's SHA-256, every closure anchor (`koffi-<target>`, `sharp-<target>`, `sharp-libvips-<target>`, `dsh-base`) is present, the asar contains the expected entries and no stray `node_modules`, and the nine fuses read back to their release values. A check failure fails the pipeline; it is not a warning.

**All nine Electron fuses are set explicitly, before any signature.** `apps/desktop/scripts/packaging/fuses.ts` pins the complete fuse set for Electron 43 with `strictlyRequireAllFuses: true` — no fuse is left to an Electron default. `RunAsNode` and the file-privilege fuses are disabled; `EnableEmbeddedAsarIntegrityValidation` and `OnlyLoadAppFromAsar` are enabled. The flip happens before signing because a fuse flip rewrites the binary and invalidates any existing signature; on Apple Silicon an ad-hoc re-sign is mandatory afterward. Two mechanical traps are pinned by construction: `@electron/fuses`' `FuseV1Options` is a *numeric* enum, so `Object.values` yields both directions and the code iterates the explicit `DESKTOP_FUSE_INDICES` (numeric keys `0..8`) instead; and `flipFuses` returns the count of binary *slices* it rewrote (the sentinel), not the number of fuses changed, so the report says "set 9 fuses across 1 binary slice(s)".

**Signing is credential-gated and reported as configured-versus-executed.** There is no single signing mode. On macOS, `apps/desktop/scripts/packaging/package.ts` signs with the `CSC_NAME` keychain identity via `@electron/osx-sign` when one is present (hardened runtime, the built-in entitlement set that already grants `com.apple.security.cs.allow-jit`), and notarizes via `@electron/notarize` when `APPLE_ID`/`APPLE_APP_SPECIFIC_PASSWORD`/`APPLE_TEAM_ID` are set; with no credentials it falls back to an ad-hoc `codesign --force --deep --sign -`, which is launchable on the build host after the fuse flip but is not a distributable signature. On Windows it signs with `@electron/windows-sign` when `CSC_CERTIFICATE_FILE`/`CSC_KEY_PASSWORD` are set, else ships unsigned. On Linux there is no signing. The `package-report.json` records, per step, whether signing and notarization were *configured* (credentials present) and *executed*, so a build that could not notarize is never misreported as one that did.

**D4 is a real Windows process-tree guarantee, executed only where it can be proven.** When the runtime root dies, every process in the DSH tree — including DSH's own detached command trees — must die with it. On Windows this is implemented in the runtime child (`apps/desktop-runtime/src/windows-job.ts`) with a Win32 Job Object created with `KILL_ON_JOB_CLOSE` and the process assigned to it via `AssignProcessToJobObject`, using `koffi` against the kernel32 API with a struct-size guard before any call. The acceptance script (`apps/desktop/scripts/d4-acceptance.ts`) forks a child that spawns a grandchild, kills the child's root with `taskkill /F /PID` (deliberately not `/T`, so the Job Object — not the taskkill tree flag — is what kills the grandchild), and asserts the grandchild is gone within the deadline while the acceptance process itself survives. This runs **only** in the `desktop-windows` CI job, on a real Windows kernel; it is never claimed as locally exercised on macOS.

**The clean-copy boot smoke is the distribution proof.** `apps/desktop/scripts/packaging/smoke-runtime.ts` forks the packaged `runtime/dist/index.js` with the *artifact's own* bundled Node, a fresh `DSH_HOME` in a temp dir, and a minimal `PATH` (`/usr/bin:/bin:/usr/sbin:/sbin`), and asserts the child reaches `runtime.ready` with a `dshVersion` equal to the manifest's DSH version, then shuts down gracefully under a bounded kill deadline. If the closure, the Node binary, or a native prebuild is wrong, this fails — it is the closest the pipeline gets to "a user double-clicks the app". It runs as the final gate of `package` unless `--skip-smoke`.

**Each CI runner packages its own platform.** Cross-host packaging is rejected by design: the closure's native prebuilds are host-specific, so a macOS runner cannot stage a correct Windows closure. `ci.yml` adds three required jobs — `desktop-macos` (macos-latest), `desktop-windows` (windows-latest, which also runs the D4 acceptance), and `desktop-linux` (ubuntu-latest) — each running `pnpm --filter @deepseek-ai/dsh-desktop run package`. They are in `all-checks-passed.needs`, so a broken package on any platform, or a D4 regression, blocks the merge.

## Facts the stage settled

- The packager's `filenamify` does **not** replace spaces (they are not reserved characters), so the output directory, the `.app`, and the executables keep the product name's spaces verbatim on every platform — `DeepSeek Harness Desktop-<platform>-<arch>` and `DeepSeek Harness Desktop.app`. The artifact-path helpers preserve the spaces; they do not hyphenate.
- A scoped store package's real path is `.pnpm/<id>/node_modules/@scope/<name>`; the container is the three path segments after the `.pnpm` segment, found with `lastIndexOf`. A store package's own `.bin`-only `node_modules` masks the container and must be checked before it.
- `@electron/fuses`' `FuseV1Options` is a numeric enum: `Object.values` returns both name and value directions, so fuse iteration must use the explicit numeric index list.
- `@electron/osx-sign` 2.x `sign({app, identity})` defaults `hardenedRuntime` on and uses the built-in entitlements (which include `allow-jit`); there is no top-level `hardenedRuntime`/`entitlements` option in 2.7.0. `notarize` takes `appPath`, not `app`. `@electron/windows-sign` `hashes` is a cross-package `const enum` a string literal cannot satisfy and must be cast.
- The standalone-Node ABI rule means the runtime's native modules are retargeted to the bundled Node, and `electron-rebuild` must never touch them; the two ABI worlds (Electron for the shell, standalone Node for the runtime) are the whole point of the split.

## Consequences

- Stage 11 exit criteria met with no pinned-source change and no new Electron surface: the release unit is reproducible (manifest + closure fingerprint), self-contained (boot smoke under the artifact's own Node, minimal PATH), per-platform (three required CI jobs), and process-contained on Windows (D4, executed on a real kernel in CI).
- New scripts: `apps/desktop/scripts/packaging/{package,staging,closure,build-manifest,fuses,verify-layout,smoke-runtime}.ts`; new devDependencies `@electron/asar`, `@electron/osx-sign`, `@electron/windows-sign` (alongside the existing `@electron/packager`, `@electron/fuses`, `@electron/notarize`); `koffi ^3.1.0` in `apps/desktop-runtime`.
- New coverage: `apps/desktop/tests/packaging.spec.ts` (fuse pin, per-platform binary path, closure-fingerprint determinism, manifest reader, and an opt-in full layout verify against a built artifact) and the extended `ci-workflow.spec.ts` (the three required per-platform jobs and the Windows-only D4 lane).
- D4's Windows execution and the Windows/Linux packaging are CI-proven, not locally proven: the local host is macOS, so the `desktop-windows` and `desktop-linux` lanes are the standing evidence for those platforms, and the Developer ID / notarization / Windows-certificate signing paths are configured-not-executed where credentials are absent.
- The updater (SPEC §28) is recorded as the release boundary but not built; stage 11 produces the artifact the updater would later move.

## Alternatives considered

- Running DSH under Electron's Node instead of a bundled standalone Node — rejected: it would collapse the two-ABI split, force `electron-rebuild` over the runtime's native modules, and tie the DSH runtime to Electron's V8/ABI release cadence; the split is what lets the runtime track a pinned, checksummed Node.
- Copying `node_modules` wholesale instead of a store-derived closure — rejected: a `node_modules` snapshot carries the developer's full tree (devDependencies, hoisted duplicates, platform-foreign prebuilds) and is not a lockfile-pinned, reproducible unit; the closure is the minimal, hashable set.
- Cross-host packaging (one runner builds all platforms) — rejected: native prebuilds are host-specific, so a single host cannot stage a correct closure for the other platforms; each runner packages its own platform.
- Leaving fuses to Electron defaults and flipping only the security-critical ones — rejected: a default is an implicit contract that changes with the Electron version; `strictlyRequireAllFuses` plus an explicit nine-fuse set makes the artifact's capability surface a reviewed, pinned fact.
- Making the packaging jobs non-blocking (observational) like `windows-native` — rejected for v1: a broken package or a D4 containment regression is a release defect, and the whole point of the stage is that the distributed unit actually boots; the three jobs are required.
- Signing ad-hoc on the CI lanes and calling it done — rejected: ad-hoc is a build-host launchable signature, not a distributable one; the pipeline instead distinguishes configured (credentials present) from executed and reports it, so a release can require the real credential path without the CI lanes needing secrets.
