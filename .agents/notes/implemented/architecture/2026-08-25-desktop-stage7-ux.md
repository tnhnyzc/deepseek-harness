# Agent Note: desktop stage 7 — desktop UX: window sizing, native menu, closed command bridge

Status: implemented

English | [中文](2026-08-25-desktop-stage7-ux.zh.md)

## Problem

Stage 7 (SPEC §16) adds the desktop-specific value on top of stage 6's functional equivalence: the native window sized for a desktop, a native application menu with platform-conventional keyboard shortcuts, and menu actions that drive the harness. The constraints are strict: DSH stays the sole owner of every agent semantic (desktop = carrier only), the SPEC says actions that affect Harness state "should dispatch to the existing DSH client service rather than another main-process API", the pinned client tree must not be modified, and the test environment has no API key.

## Decision

**Window sizing.** `apps/desktop/src/main/window.ts` creates the window with `useContentSize` and a 1280×800 content rectangle, minimum content 1024×600: the platform chrome (standard frame, macOS traffic lights) stays Electron's, and the DSH content fills the content rectangle edge to edge. The full-bleed gap the shell CSS left around the pinned client frame is fixed in `apps/desktop/src/renderer/styles.css`.

**Native menu.** `apps/desktop/src/main/menu.ts` builds the SPEC §16 menu as a pure template function, `buildApplicationMenuTemplate(ApplicationMenuOptions)` — the shell supplies the app name, the platform flag, devTools availability, the command sink, and the about action, so the template unit-tests with recorders instead of an Electron app — and installs it with `installApplicationMenu`, which also sets the about-panel identity (`DeepSeek Harness Desktop`, app version). The surface: macOS app menu (About, Settings… `CmdOrCtrl+,`, Services, Hide/Hide Others/Show All, Quit); File (New Session `CmdOrCtrl+N`, Open Workspace… `CmdOrCtrl+O`, Close Window — plus Settings… `CmdOrCtrl+,` on the non-macOS platforms, which have no application menu; each platform carries exactly one Settings item); the standard `editMenu` role; View (Toggle Sidebar `CmdOrCtrl+\`, Zoom In / Zoom Out / Reset Zoom roles, Developer Tools only while the app runs unpackaged); Session (New Session, Cancel Current Run, Rename Session); the macOS Window role; Help (the documentation and runtime-log entries are disabled with tooltips — the fork has no published documentation and runtime logs stay in memory until the diagnostics stage; non-macOS About → `app.showAboutPanel()`). There is no Cmd/Ctrl+K (the pinned client has no command palette), no OS-global shortcuts, and no Escape binding (Escape keeps the pinned UI's own semantics).

**The closed command bridge.** The menu expresses exactly six intents — `new-session`, `open-workspace`, `cancel-run`, `rename-session`, `open-settings`, `toggle-sidebar` — a closed vocabulary in `apps/desktop/src/shared/desktop-command.ts` (channel `dsh-desktop:command`, guard `isDesktopCommand`). The names are kebab-case UX intent names on purpose: the SPEC §31 boundary scan keeps the desktop transport layers free of dotted business-RPC literals, and a command named like an RPC method is that decay by definition. A menu click sends one vocabulary member from main to the app window's main frame, never a broadcast. The preload (`src/preload/index.cjs`) exposes `window.dshDesktop.onDesktopCommand`, which re-applies the guard before the payload reaches the page: the enforcement point is the page boundary, not main's intent. The renderer adapter (`src/renderer/desktop-commands.ts`, installed from `src/renderer/main.ts`) translates each intent into the existing pinned DSH client action — the same DOM gesture a user would click — and nothing else:

- `new-session` → the "New session" button; `open-workspace` → the "Add workspace" button (the add-only picker consumes the open and raises the composed directory flow directly, which drives `host.pickDirectory` into the native dialog); `cancel-run` → the composer's "Stop generating"; `rename-session` → the selected row's action menu, first item (the pinned source's fixed item order: rename, fork, archive); `open-settings` → the sidebar's settings trigger (the only `aria-haspopup="dialog"` button in the sidebar column); `toggle-sidebar` → the sidebar fold button.
- Product copy is locale-painted (zh or en), so each gesture matches the closed label set of both shipped locales, not one language's strings.
- While the shell screens are up (no live client tree) and in states the tree cannot act on (no selected row, nothing generating, no rendered affordance), the command is a deterministic no-op: the menu stays safe in every state instead of the page guessing.

No wire method is added, main never mutates Harness state, and the pinned client tree stays untouched — stage 7 added no modification (the stage 8 shared set U1–U3 is later; `2026-08-26-desktop-stage8-correctness.md`).

**Carrier defects fixed in this stage.** (1) The desktop composition overlay (`apps/desktop-runtime/src/composition.ts`) inserted only the native directory picker's *host* row; the composed boot graph also needs the *client* row of `@deepseek-ai/dsh-client-ui-directory-picker-native`, and without it the "Add workspace" affordance never raises the native flow (proven absent by probe: `addWorkspace:false`). The overlay now inserts both rows and `apps/desktop-runtime` declares the surface package as a workspace dependency. (2) Build order: `apps/desktop-runtime/tsdown.config.ts` bundles `lib/types/*.js` entries — **tsc emits, not source** — so running tsdown alone silently bundles stale emits. The runtime builds as `tsc -b` (which emits `lib/types`) then tsdown; the root `pnpm run typecheck` performs that emit.

**Tests.** `apps/desktop/tests/menu.spec.ts` (11): template structure on both platforms, accelerator registration plus no-Esc bindings, devTools gating, File/Session order, the Help disabled placeholders plus the non-mac About click, the exact command dispatch sequence for every command, vocabulary closure, `isDesktopCommand` accept/refuse, the preload's vocabulary-mirror lockstep (regex over the mirror set in `index.cjs`), and the IPC channel inventory scan of `src/main` + `src/shared` against the known closed channel set (asserted non-vacuous). `apps/desktop/tests/desktop-ux.spec.ts` (10): built-app E2E (self-skips without the artifacts, scripted deterministic SSE provider on the `DEEPSEEK_BASE_URL` seam, console gate): the 1280×800 content size plus the minimum clamp; the live native menu's surface plus registered accelerators; out-of-vocabulary and object bridge payloads refused (no state change, no console errors); the sidebar flip through the bridge; File > New Session creating a real DSH session; File > Open Workspace… driving the composed directory flow into the OS dialog (`dialog.showOpenDialog` patched in main: exactly one call with `openDirectory`, cancelled, no workspace added); Session > Cancel Current Run cancelling a mid-stream turn; Session > Rename Session renaming durably through the rename dialog; the platform new-session accelerator registered on the live menu; Settings opened through the app menu (macOS) / About through `showAboutPanel` (other platforms).

## Facts the stage settled

- **Blank-session reuse** (DSH semantics shared with `dsh web`): `connectWorkspace` (`packages/client/runtime/src/client/workspaces/service.ts:89-111`) reuses the target workspace's existing non-archived blank session (workspace membership plus same cwd), and `startSession` (`:177-192`) silently no-ops when no target resolves. "New session" from a *blank* current session therefore does not create a second session — it reuses the blank one. Menu/E2E consumers must make the current session non-blank with a turn before asserting a count increase (stage 6's parity test increments only because its current session is non-blank).
- **Electron's live menu**: `MenuItem.role` reports lowercased (`zoomin`, `zoomout`, `resetzoom`, `toggledevtools`) and the macOS `resetZoom` item labels "Actual Size" — assert roles, not labels. `accelerator` returns the registered template string verbatim. CDP-synthesized key input (the only input an automated driver has) never reaches the OS-level accelerator registration, so the key press itself stays in the manual smoke while the automation proves the registration and that the bound command dispatches through the item click.
- **The rename dialog**: its input is `aria-label="Session name"` / `会话名称`, its confirm button `Rename` / `重命名`; row-action menus portal to `document.body` and close on a document-level Escape keydown.

## Consequences

- Stage 7 exit criterion met: the desktop-specific value (native chrome, native menu with platform accelerators, menu-driven UX actions) is in place with every harness semantic staying in the pinned DSH client and the pinned client tree unmodified by stage 7 (the stage 8 shared set U1–U3 is later).
- Full desktop suite: 146 (125 baseline + 11 menu + 10 desktop UX).
- The closed command vocabulary is the standing seam for later stages: a menu affordance added by a later stage is one vocabulary member plus one adapter gesture plus its tests, never a new wire path.
- The desktop UX surface drives the pinned client through DOM gestures: a future pinned-client relabel or re-layout breaks the adapter's label sets, and the desktop-UX E2E is the tripwire.

## Alternatives considered

- Main-process harness mutation (menu clicks dispatching harness RPCs from main) — rejected: SPEC §16 requires dispatching to the existing DSH client service rather than another main-process API, and a second write path would bypass the client's UI state machine.
- New wire methods for the menu actions — rejected: the carrier-only rule; every needed semantic already exists as a pinned-client affordance, and new methods would duplicate the client's ownership.
- Renderer keydown listeners for the shortcuts — rejected: the SPEC wants platform-conventional behavior, and the native menu's accelerators are exactly that; renderer listeners would double-bind and fight the UI's Escape semantics.
- Real-API provider for the UX E2E — rejected as in stage 6: nondeterministic and key-gated; the `DEEPSEEK_BASE_URL` scripted seam keeps the provider's wire path real.
- OS-level key synthesis (AppleScript / robotjs) for the accelerator smoke — rejected: platform-specific and flaky in a portable suite; the accelerator's command dispatch is already proven through the menu-item click.
